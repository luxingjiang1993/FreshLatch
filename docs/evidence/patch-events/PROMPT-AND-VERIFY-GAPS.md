## 已写明、这次不改

- 生成请求的模型字段只读 `DEFAULT_MODEL`。本页不写模型名字面量。
- `models.py` 里 `default_llm.temperature` 为空。预注册写明温度缺省则该次生成作废。正式入口不把温度补成 0。
- C、T、B1 的生成阶段是 `rewrite`。B2 的顺序是先 `claim` 再 `diff`，实现在 `run_arms._generate_edit`，它只调用注入的 generator。
- C 不调用核验，生成成功即放行，记录里的 evidence id 写成空。
- T 在核验之前先做 chunk 绑定：evidence id 必须能解析，且属于本次已入库 T1。绑定失败则拒绝，理由是「证据未绑定已入库 T1」。核验不过则 hard reject。
- B1 在生成之后核验，不过则拒绝。这次拒绝的臂是 B1，不是 T。
- B2 核验不过不因此 hard reject。核验结果记在 `reverify_ok`，决定仍是放行。
- 消融只在 T 上：拿掉 chunk 绑定、拿掉自动核验、hard reject 换成 soft warning、检索臂换成 BM25。`hybrid+rerank` 另记一列，不进主比较。
- 核验回调的返回键是 `ok`、`score`、`reason`。非数字的 `score` 记成空。C 没有验证分数。

这些开关已经在 `patch_events_arms.py` 和 `patch_events_ablation.py`。这次不改判定。

## 提示词正文缺的句子

1. 模型输出的形状。代码只要求生成器返回 `after_text`，B2 的 claim 阶段返回 `claim_text`。没有一句规定模型看到的是一行 JSON、纯文本，还是 diff。
2. C 是否看见证据。预注册写无证据改写、不绑定 chunk。生成请求仍带 `evidence_id` 和 `evidence_text`。没有一句规定提示词删掉这两段，还是留着但禁止使用。
3. T 的证据从哪来。预注册写 T 的检索读生产检索赋值。请求里已经放了候选的 `evidence_text`，代码并不检索。没有一句规定提示词只根据给定 T1 chunk 改写，还是先按检索模式取 chunk 再改写。
4. claim 是什么。预注册写先从主张得到 claim，再生成 diff。没有一句定义 claim 与 `before_text` 的差别，也没有一句定义 diff 相对 `after_text` 的形状。
5. 四臂是四份正文还是一份正文加约束。做法表把四臂分开，没有一句规定 rewrite 阶段各写一份，还是共用一份。
6. 生成提示词允许出现的段落。评委细则的「不许加提示，不许改措辞」只约束评委。没有一句列出生成提示词可以出现主张、证据、修改类型或检索模式中的哪些。
7. 无法修改时模型返回什么。代码把缺 `after_text` 或 `void` 记成生成失败。没有一句规定提示词要求模型在无法修改时输出的标记。

因此没有单独的提示词版本文件。四臂各自用哪一份，要等上面七句写明之后才能编号。

## 自动核验缺的句子

1. 「核验不过」的操作定义。预注册只写 T 与 B1 核验不过则拒绝，B2 不因此 hard reject。没有一句把「不过」写成可执行谓词。
2. 「与所绑 T1 chunk 一致」怎样比较。这句话定义的是构造金标里的正确修改，不是运行时拿 `after_text` 对 `evidence_text` 的算法。没有一句规定一致是子串包含、同一数字，还是别的关系。
3. 「与证据矛盾，或证据不能支撑」怎样判定。评委问题 A 和问题 B 只发给外部评委。没有一句说自动核验复用这两句，也没有一句说不复用。
4. `score` 的取值和方向。有排序分数的臂按分数从高到低取前 k，同分按 `claim_id`。没有一句规定分数的范围、高分是否更该放行，或没有分数时如何排序。
5. 核验入参之外还看什么。现有调用只传入臂、`claim_id`、`after_text`、`evidence_id`、`evidence_text`。不传入已入库集合，不传入修改类型，不传入构造金标。chunk 是否已入库 T1 已由绑定闸在核验之前处理。没有一句规定自动核验在这道闸之外还要看什么。

因此没有可调用的自动核验函数。不返回 `ok`、`score`、`reason` 的新实现。
