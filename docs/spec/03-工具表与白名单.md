## 3.4 `spawn_critic(focus)` 词表(#14 定稿)

- **封闭枚举 6 值**,与语料金标维度同构(§2.6);英文 slug 为代码常量(初始集,变更须同时改常量、CONTEXT.md 词表与一致性单测):

| slug | 中文 | slug | 中文 |
|---|---|---|---|
| `competitor_pricing` | 竞品价格 | `cost_model` | 成本模型 |
| `regulatory_stance` | 监管口径 | `market_structure` | 市场结构 |
| `interview_reversal` | 访谈改口 | `tech_ecosystem` | 技术生态 |

- **focus 可选,省略 = 不限方向**;不设占位枚举值(「主动不限」与「忘了传」在日志归因上是两个事件)。
- **focus 指「去哪里找反证」,不是「期望什么判定」**:must_unknown 主张照样按业务主题传维度(Critic 按方向找、找不到,正是 must_unknown 的本义);focus 与判定结果挂钩 = 答案泄漏,红线。
- **非法值处理**:调用边界硬校验(tool call 进循环体之前),整个调用被拒,错误信息回列全部合法值(API 错误设计惯例,模型自我纠正率最高);**重试消耗 Lead 的 18 步步数预算**(防穷举撞词表)。
- 每次派驻的 focus 进 run 日志(顺带,事后可看 Lead 的派驻分布)。

## 3.5 Skill 文件与工具表的关系(#10)

- 仓库根 `skills/<slug>/SKILL.md` + `references/`;`name` 英文 slug,description 与正文全中文。
- **禁令唯一真相在代码**;skill 只写「约束存在 + 理由 + 被拦后的正确动作」(教义层),「拦截 → 纠正」写成显式对照表,每条注明「以代码返回的错误信息为准」。
- 四份文件:`reverify`(Lead,≤18 步)/ `devil_advocate`(Critic,≤8 步,只找已死)/ `freshness_audit`(Auditor,单轮判定 SOP;`references/verdict-rubric.md` 是判定口径单一真相)/ `memory_forensics`(完整纪律版,frontmatter description 明示「W9–W12 起由 Runner 加载」,本期不挂载)。
- **一致性单测 4 断言**(进 `tests/unit/`):① frontmatter 规则(name ≤64 小写连字符、description ≤1024、无 XML 标签、name=目录名、metadata ~100 词、正文 ≤500 行,纯 Python 重写 check_a_skill 规则,不引其工具链);② skill 正文+references 出现的工具名 ⊆ 该角色白名单代码常量;③ `focus-dimensions.md` 6 值 == `FOCUS_DIMENSIONS` 常量;④ 对照表「场景→动作」映射存在(不断言文案)。
