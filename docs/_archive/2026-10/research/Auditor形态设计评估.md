## §1 问题与前置约束

**问题**:Auditor 的语义在词表已定(短循环 Agent,判 fresh/stale/unknown,不得拥有放行权),
但落地形态欠账随 W5–W8 实装窗口临近必须拍板;且「Lead 判定 × Auditor 判定」的仲裁结构
在规格与代码里都是空白(`rule_gate.py` 对 Auditor/verdict 零钩子)。

**grilling 期间查实、改变问题定义的四个硬事实**:

1. **形态在规格里已拍过**:spec 03 §3.2「Auditor(W5–W8)= 单轮判定 SOP:一次 structured-output
   调用(输入主张 + 证据包,输出 verdict + 理由),freshness_audit.md 即其 system prompt;
   无工具、无循环,判定完全可复现。**推翻此形态须新工单**(#10 不开暗门)」。#20 工单 body
   挂的候选(甲 MCP server / 乙 进程内子代理 / 丙 工具函数)是查规格**之前**写的——乙的实质
   即规格既定形态。故本工单的真问题重定:**c5/c6 + #19 的新证据是否构成推翻理由**;
   否则剩余价值是拍规格没拍的子决策(仲裁结构、在场机制、MCP 暴露事项、验收采样)。
2. **MCP 暴露是另一笔独立登记**:spec 03 §3.1「MCP 暴露(retrieve/read_source/reverify_claim/
   list_memories)是 W5–W8 事项」——把 Lead 工具经 MCP 对外,无对应调用方需求记录。
3. **c2 的派驻失灵定性是最强先例**:「自信地错恰是派驻最不会触发的时刻」——任何
   「Lead 想叫才叫」的派驻在自信错误面前系统性缺席,c2 修复因此改为结构性自动触发。
4. **#19 的教训分层正确**:c5/c6 事故在「指令不在场」,不在「进程不隔离」——同进程内的
   Critic/Lead 出错点在人格未接线;把 Auditor 搬出进程修错了层。

**前置约束(不得触碰)**:Auditor 不得拥有放行权、不得改主张正文(词表);规则闸管不变量
不管语义质量(c5 二修两次否过语义入闸,继续有效);绿灯唯一出口在闸;判分口径 W4↔W12
同尺;额度纪律(行为跑触发归判定人);规格 T6 的 skills 注入结构(#19 已拍接线)。

## §3 逐路线评估

| 维度 | 甲(MCP) | 丙(函数化) | 丙′(终裁) | 丙′′(全人审) | 丙4(闸校验) | 丙5(全派驻) |
|---|---|---|---|---|---|---|
| 复现性 | 跨进程多序列化/版本面,承诺变弱 | 不适用(角色消失) | Lead 工具语义架空 | 无机器判定可复现 | 打回-重试往返,轨迹噪音 | stale/unknown 路径空烧调用 |
| 根因命中 | 修错层(#19 教训:缺口在指令在场不在隔离) | — | 推翻 spec 另一面 | 人审负载膨胀 | 强制性住在错误信息里,依赖模型读懂服从 | 浪费面 > 收益面 |
| 安全不对称 | — | — | 单点(终裁即放行链一环) | 过度保守 | fail-closed 等价 | fail-closed 等价 |
| 与既有架构 | 违背「md 即 system prompt」单一真相 | 违反词表 | spec 已钉 Lead 持判定工具 | 与 HumanLatch 设计初衷冲突 | 模式现成但多此一举 | checkpoint 同构但触发点过粗 |

**被否理由写透**:

- **甲被否**:隔离收益近零(Auditor 无工具无循环,只读本进程组装的证据包,攻击面最小),
  而复现承诺跨进程变弱;#19 已实证事故点在指令不在场,搬进程修错层。
- **丙被否**:语义判定是 LLM 判断,函数化 = 取消 Auditor 角色,违反词表与「推翻须新工单」精神。
- **丙′(终裁)被否**:spec 钉死 Lead 持有 reverify_claim/mark_stale,终裁等于暗改工具语义。
- **丙′′(全人审)被否**:真分歧才是人审负载,一律 unknown 把机器判得对的多数情形也推给人,
  是 (丙′′′) 的严格超集。
- **丙4(纯闸校验)被否**(Anthropic 否的原推荐):fail-closed 程度与丙6 等价,但把强制性
  住在「模型读懂并服从报错」上——c5/c6 的全部教训就是别建立在那一层;且拒绝-重试往返
  纯成本。原推荐撤销,改丙6。
- **丙5(全派驻)被否**:多数主张不走 fresh 路径,每条自动派驻的空烧面大于收益面;
  且异议在判定前可见的收益没有结构兜底(「读了异议仍自信地错」)。
- **附1(MCP 实装)被否 / 附2(留位)被否**:无调用方的能力暴露是负安全资产;连复验单 UI
  都走进程内 FastAPI,「为未来预留」在本仓连故事都讲不通;显式不做(C)代价最低、信号最清。

## §4 拍板与子决策

**拍板:确认规格形态(乙′,不推翻);仲裁 = 从严并联(丙′′′);在场机制 = fresh 钩子内自动触发
Auditor + 闸前置兜底(丙6);MCP 暴露显式不做;记 ADR-0009。**

子决策:

1. **形态确认(乙′)**:单轮 structured-output、无工具无循环、freshness_audit.md 即 system
   prompt;证据包 schema 版本化(进验收判据)。
2. **预登记重开触发器**:W5–W8 评测若显单轮判定对合取主张噪声过大 → 形态重开新工单。
   拍板带诚实的退出条件,不拍死。
3. **从严并联(丙′′′)+ 3×3 落档真值表**(实现规格,词表「双判一致」引用本表):

   | Lead \ Auditor | fresh | stale | unknown |
   |---|---|---|---|
   | **fresh** | **fresh(唯一绿格)** | stale | unknown |
   | **stale** | stale + 异议记录 | stale | stale |
   | **unknown** | unknown + 异议记录 | stale | unknown |

   规则:含 stale 落 stale;无 stale 含 unknown 落 unknown;全 fresh 才绿。Auditor 缺席时
   fresh 请求不落(打回/触发后重试)——缺席不构成任何绿格。
4. **在场机制(丙6)**:`_t_reverify_claim(status=fresh)` 钩子内自动触发 Auditor
   (与 `_auto_critic_checkpoint` 同点同构,模式已在仓内实证);闸前置不变量
   `auditor_verdict` 在场且非 dissent 作为 fail-closed 兜底;**stale 路径不强制**
   ——错误不对称推论:fake-fresh 是灾难方向且自动层仅此一道,强制双人;fake-stale 可恢复
   且已有两层(#19 Lead 侧修复 + HumanLatch),第三层边际收益配不上每条调用;
   `spawn_auditor` 在 stale 路径保留为 Lead 主动工具(异议记录的技术载体),叫不叫交还模型。
5. **MCP 暴露:显式不做**,登记地图 Out of scope。
6. **W5–W8 验收 pre-registration(判据先于实装写死)**:
   - 样本:全量 12 条;n=3、temp=0、qwen-flash(端点锁定沿用)、证据包 schema 版本随报告登记;
   - 通过线:① 零 must_stale→fresh(双人拦截下更易达成——报告抬头须备注「轻松达成 ≠ 结构
     无效」,防误读);② must_fresh 水平**不得低于 #21 实测并留档的基线**(锚实测值非期望值;
     **#21 未跑则本验收不得启动**——依赖边天然防攒批);③ S1/S2 分歧率只落档不报成败
     (操作化定义:每主张每跑 Lead stale/unknown × Auditor fresh 计 S2,反之为 S1);④ 结构
     断言:每条 fresh 均有 auditor_verdict 在场且 schema 版本断言单测绿;
   - 触发:判定人本人;不与 #21 攒批,#21 先行、本验收独立触发。
7. **与 #19 的 reconcile(工单条款正面回答)**:维度铁律单一真相在 verdict-rubric.md,
   Auditor 的 system prompt 注入走 #19 已拍的 skills 接线;Lead 侧自查保留(#19 范围);
   W5–W8 实装时 Auditor 侧铁律是引用点新增,不是真相迁移——两工单无先后等待,各自落地。

### §4.4 ADR 三条件(为何记 ADR-0009)

「双判一致 + Auditor 在场」写进规则闸不变量:难反转——W5–W8 及后续验收建立其上,事后放宽
等于悄悄拆双人拦截却保留「验过」叙事(纪律 #7 追问通过:破坏实验意义);反直觉——「审核员
可以投反对票但不能缺席」非默认值,未来读者会问为什么;真实取舍——丙4/丙5/丙′/丙′′ 被否的
取舍在上表写透。三条件齐备,记 `docs/adr/0009-双判一致与auditor在场不变量.md`。

## §6 面试讲法(grilling 预案)

**Q:Auditor 为什么不做成 MCP server?隔离不是越强越好吗?**
A:隔离收益要看攻击面:Auditor 无工具无循环,只读本进程组装的证据包,几乎无攻击面可隔离;
而复现承诺跨进程变弱(序列化、版本、部署多一层)。更根本的,#19 已实证这类事故点在
「指令不在场」不在「进程不隔离」——搬进程修错了层,把 wiring 接通才是正解。

**Q:「审核员可以投反对票但不能缺席」不矛盾吗?**
A:不矛盾,这是 c2 事故的同构防御。c2 的定性是「自信地错恰是派驻最不会触发的时刻」——
派驻交给模型自觉,系统性缺席。所以在场是结构性的:fresh 尝试的钩子内自动触发,强制性住在
触发器里,不住在错误信息里(闸前置只做兜底)。而 stale 路径不强制,是错误不对称推论:
fake-fresh 灾难方向且自动层仅此一道,必须双人;fake-stale 可恢复且已有 #19 + HumanLatch
两层,第三层配不上成本。

**Q:为什么 stale 路径 Auditor 不强制?c5/c6 正是假 stale 方向。**
A:纵深防御不等于均匀纵深。c5/c6 的自动修复在 #19(Lead 侧维度自查+注入),人审兜底在
HumanLatch;Auditor 强制第三层烧每条主张的调用,边际收益配不上。stale 路径保留主动派驻,
异议来了会结构化挂卡——但叫不叫交还模型,这一层失守有人接,所以允许它失守。

**Q:为什么不冲突一律 unknown,最保守?**
A:保守要看负载去向:一律 unknown 把机器判得对的多数情形也推给人,人审膨胀;从严并联只在
真分歧时产生人审负载,是它的严格子集。且「含 stale 落 stale」与「无 T1 不得 fresh」一样,
是单向不对称的:最坏结果进人审,绿灯方向不开口。

**Q:MCP 是现在的标准做法,为什么显式不做?**
A:接口的存在需要调用方。复验单 UI 走进程内 FastAPI,不经过 MCP;「W5–W8 事项」只是排期
登记不是需求。无调用方的能力暴露是负安全资产——每多一个对外面就多一个滥用面,收益为零。
真出现调用方时新工单进来,四个工具规格现成,回 reopen 成本极低。

**Q:验收里「不得低于 #21 实测基线」这条怎么执行?**
A:#21(c5/c6 修复)先行验收并留档实测水平;Auditor 实装验收启动前检查该档存在,不存在就不
启动——依赖边天然防攒批。这条不等式把两张工单的验收锁在一起:修 A 坏 B 会被抓出来,而不是
在合并报告里被平均掉。若 #21 自身未达标,基线锚实测值而非期望值,不等式依然可计算。
