## 1. 问题 + 前置约束

### 1.1 要拍什么

Batch 2 半激活之后：是否/何时启用**跨轮腐烂重检**（已写 `validity_basis` vs 语料现算不符时谁比、何时比、不符降到哪）。此为**产品行为变更**，必须预登记。

验收层：**预登记文档 + 降级路径 invariant**；不得把「跨轮重检上线」讲成统计结论或 latch 证明。

### 1.2 前置约束（勿重开）

| 前置 | 来源 | 锁死作用 |
|---|---|---|
| 档 2 renew 半激活；fresh 不构造 basis | ADR-0017 | 无 basis 的 Agent fresh 不得被 3b 当成腐烂 |

## 4. 拍板 + 逐项子决策

1. 锁跨轮重检产品行为；本会话不 `/implement`；实装/规格另票 + 负例预登记。
2. 双触发：复验/迷你复验入口机械前置 **且** UI 拉单/渲染；共用 `check_basis` + `apply_rot`，均持久化。
3. 范围：`fresh` ∧ basis 非空；`voided` 跳过；无 basis 的 fresh 跳过。
4. 不符 → `unknown` + 机械码；不进 Lead；不自动 `void`。
5. 保留 `validity_basis` 与 `last_confirmed_at`；重复检幂等。
6. 形状：单对象今日；list 全员受检（ADR-0024）；禁只比 `[0]`。
7. `apply_rot` 写 `latch_log` 机械条目；不解释成模型好坏。
8. 套套：现算语料，禁读库列。
9. 落点：ADR-0025 + 本评估 + CONTEXT/契约；关地图 #138；另开实装/规格承接。

### 预锁 invariant 可引用句（实装前锁死）

> 档 3b：对 `status==fresh` 且 `validity_basis` 非空的主张，复验入口与 UI 拉单/渲染均须经同一 `check_basis`（语料现算 sha256，禁读库列）；不符则 `apply_rot` → `unknown` + 机械码（如 `BASIS_CHECKSUM_MISMATCH`），写 `latch_log`，保留 basis 与 `last_confirmed_at`，且复验入口不进 Lead。无 basis 的 fresh 不检。本句不得升格为统计结论或「checksum 已证明 latch」。

## 6. 面试讲法

**Q:为什么不先做 3a 再做 3b？**
A:3b 读的是**已写** basis。今日 renew 已写；跨轮腐烂正是产品承诺所在。等 3a 等于让有牙的半边继续空转。

**Q:为什么掉 unknown 不掉 stale？**
A:stale 要求可点回的 T1 反证叙事。checksum 腐烂是机械事实，硬塞 evidence 是假反证。unknown + 机械码更诚实。

**Q:为什么 UI 也要写库？**
A:选了双触发。只提示不写 = 打开复验单仍显示 fresh，牙齿在展示层假活。

**Q:这证明 latch 了吗？**
A:没有。预锁句禁止升格。只证明「带 basis 的绿灯在语料变了之后会机械掉 unknown」。
