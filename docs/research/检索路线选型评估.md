## 1. 问题:我们要做什么决策

FreshLatch 的复验主链里,Lead Reverifier 调 `retrieve(query, source_type, as_of)` 查语料。这个存储/检索层选什么实现,直接影响四件硬需求:

| 硬需求 | 出处 |
|---|---|
| `as_of=T0\|T1` 换源过滤是产品核心动作,过滤必须干净 | 立项切片 §4;工单 #5 |
| `source_type`(私有/公开)维度过滤 | 立项切片 §8 |
| 检索结果必须能点回原文(`doc_id` + 定位),`validity_basis = doc_id + checksum` | 立项切片 §8/§13 |
| 评测期运行时纯本地不出网,must_stale 金标可复现 | CONTEXT.md「金标」「检索纪律」 |

规模前提(**立项切片钉死的红线,不是假设**):合成中文语料,20–30 篇 T0/T1 文档,10–15 条主张。

## 2. 规模经济学:先算账,再谈选型

选型的第一性问题不是「哪条路最好」,而是「这个规模下,哪类问题真实存在」。

- 20–30 篇文档 ≈ 数百个 chunk。暴力余弦打分(即便有向量)= 数百 × 1024 次乘加,**微秒~毫秒级**;BM25 对数百文档打分同样毫秒级。
- 几百篇 ≈ 1 万上下 chunk。暴力余弦 ≈ 1000 万次乘加,numpy 下**毫秒级**。
- FAISS 的存在意义:**十万级以上**向量,暴力扫不可用或内存装不下,才需要 ANN(IVF/HNSW)。

结论:**从 20 篇到几百篇,计算从来都不是瓶颈,瓶颈只可能是「语义召回」(措辞改写导致字面匹配漏掉)**。因此——

> 规模增长时真正需要加的是 **embedding 这一打分路**,而**从来不是 FAISS 这个库**。把「以后要混合检索」等同于「现在要装 FAISS」,是这份选型里最需要纠正的直觉。

## 3. 候选路线

### 路线 A:SQLite + BM25(纯词法,零重依赖)

- **存储**:SQLite,chunk 一行,`doc_id / source_type / as_of / doc_version / checksum / clause_id` 全是列,过滤 = WHERE 子句。
- **打分**:`rank_bm25` 的 BM25Okapi(纯 Python,无 C 扩展,Windows 直接跑)+ `jieba` 中文分词。两者都是纯 Python 轻依赖。
- **先例**:`project 多agent/src/missions/rag.py` 已验证零依赖词法检索 + 全量引用模型离线可演示;`rank-bm25==0.2.2` 在 `RAG-cy/requirements.txt` 有 pin 先例。

### 路线 B:SQLite + 多 stage 打分管线(分层折中)

- 存储同 A(不变)。
- 打分层设计为管线:`recall(BM25) → [vector 融合] → [rerank 精排]`,本期只实装 recall;后两个 stage 是骨架 + 空实现。
- schema 今天就把 `vec` 列建好(空),向量路启用 = ingestion 期 DashScope 预计算 + numpy 本地余弦,**翻开关而非重构**。
- 熔断条件写进规格:联调发现 must_stale 案例因同义改写漏召回 → 启用 vector stage。

### 路线 C:Chroma

- 立项切片 §8 点名的候选之一。元数据过滤是其强项,但:
- 引入 chromadb 新重依赖,参考库无先例;
- 它唯一的增量优势(embedding + 元数据过滤),SQLite 零额外成本全给;
- 在「运行时纯本地」纪律下多一个嵌入式向量库进程,演示便携性变差。

### 路线 D:FAISS + BM25 混合 + bge-reranker(重栈全套)

- 参考实现:`CASE-高效召回/`(FAISS + DashScopeEmbeddings + BM25Okapi + bge-reranker-base + 手写 MultiQueryRetriever),代码现成。
- 依赖成本:`faiss-cpu`(原生扩展)+ `modelscope + transformers + torch`(reranker 权重数百 MB)。
- 结构性短板:**FAISS 原生没有元数据过滤**,langchain 的 FAISS wrapper 过滤支持很差;`as_of=T0|T1` 过滤得绕(外挂 store 或扫后过滤)。
- 与 §2 对照:20–30 篇规模下,rerank 的召回增益测不出来;must_stale 金标复现反而背上一个非确定性组件。

## 4. 逐路线评估

| 维度 | A: SQLite+BM25 | B: 分层管线 | C: Chroma | D: FAISS 混合 |
|---|---|---|---|---|
| as_of/source_type 过滤 | ✅ WHERE 子句 | ✅ 同 A | ✅ 内置 | ⚠️ 需绕 |
| 运行时离线可演示 | ✅ 完全 | ✅ 完全 | ✅ 但多进程 | ⚠️ 权重可离线,依赖重 |
| 依赖重量 | 极轻(纯 Python×2) | 极轻 + 骨架 | 重 | 最重(faiss+torch) |
| 同义改写召回 | ⚠️ 弱(靠改写查询+全文兜底) | ⚠️ 弱,但留了翻开关 | ✅ 强 | ✅ 最强 |
| 金标可复现性 | 最优(全确定性) | 优(启用向量前有明确触发条件) | 中(API 漂移变量) | 中(rerank 非确定) |
| 规模升级路径 | 存储不变,加 vec 列 | 同 A,管线已就位 | 换库成本高 | 本就为重规模设计,但 10 万篇以下用不上 |
| 参考代码先例 | rag.py(词法+引用) | 综合 rag.py + CASE | 无 | CASE-高效召回 全套 |
| 面试叙事 | 按规模选型 | 决策纪律(触发式启用) | 难自圆 | 简历驱动嫌疑 |

## 5. 已随本评估一并拍板的两项

- **embedding 本期不用**:20–30 篇规模下,Lead 改写查询 + top_k 放宽(取 top 10)+ `read_source(doc_id)` 全文兜底(ground truth 本就是原文)足够缓释词法弱点;DashScope `text-embedding-v4` 预计算 + `vec` 列留作插座。
- **引用模型沿用 `rag.py` 的 Chunk/RagCitation 并扩展**:`source_type / as_of / checksum` 三字段进 Chunk 元数据;`clause_id` 继续承担点回定位(文档内 `#` 锚点)。与 ADR-0001 模块划分一致,改动最小。
- **语料 checksum 与污染文档位**:数据 + 测试双留位——ingestion 输出含 checksum 列、manifest 含 `pollution_slots` 字段(本期为空)、`gates/` 有闸门单测占位,本期不填内容。

## 6. 最终评估

**推荐排序:B > A > C > D。**

- **B 对 A 的增量**:几乎零成本(管线骨架是纯 Python 设计),换来的是「何时上向量路由评测数据触发,而非拍脑袋」的决策纪律,以及面试时完整的升级叙事。若追求极简、连格子都不想留,A 也是站得住的选择。
- **C 被否**:为一个零增量优势付重依赖,grilling 面试里答不出「为什么不直接用 SQLite」。
- **D 被否**:§2 的规模经济学——几百篇都不需要 FAISS,何况 20–30 篇;混合+rerank 的全部增量价值在此规模下不可测,而依赖重量、过滤短板、复现变量是即期成本。「考虑过并明确拒绝」比「import 了全套」更能展示判断力。

### 7.6 登记册总结:取舍逻辑一句话

> **本期 = 结构感知分块 + BM25 + 查询改写由 Lead 承载 + 全量留位;一切 LLM 参与的检索增强(假设性问题、HyDE、MultiQuery 并行、rerank)统一由「金标命中回放不过」这一熔断条件触发,触发后在对应工单从本册点菜。** 规模(20–30 篇)决定不需要,可复现纪律(评测期零出网、must_stale 可复现)决定不能多,熔断机制决定不丢。

## 8. 面试讲法(grilling 预案)

**Q:你们的 RAG 怎么做的?为什么不上向量数据库?**

> 语料层用 SQLite,chunk 的 `as_of/source_type/doc_id/checksum` 全是列,换源对照过滤就是一条 WHERE——这是我们产品的核心动作,所以过滤干净是第一判据。打分是管线:`BM25 recall → 预留的 vector 融合 → 预留的 rerank`。本期 20–30 篇合成语料只启用词法路;向量路的存储格(`vec` 列)今天就在 schema 里,ingestion 期预计算 DashScope embedding,运行时本地余弦,不出网。

**Q:纯 BM25 漏召回(同义改写)怎么办?**

> 三重缓释:一,Lead 负责改写查询,把口语主张改写成文档措辞;二,20–30 篇规模下 top_k 可以放宽到 10,候选集本来就大;三,ground truth 是原文不是 chunk,`retrieve` 之后还有 `read_source(doc_id)` 全文兜底。并且我们写死了熔断条件:联调中 must_stale 案例若因措辞改写漏召回,就启用向量融合——启用由评测数据触发。

**Q:规模到几千几万篇怎么办?**

> 存储层不换——SQLite 单文件撑几百万行 chunk 无压力,过滤逻辑不变。打分层加路:vector 融合翻开关,rerank stage 填实现。FAISS 这类 ANN 库要到十万级以上向量才有存在价值,那时候替换的是打分层,而且藏在 `retrieve()` 接口后面,语料存储和 gates 都不动。

**Q:为什么不用 Chroma / LangChain 的现成方案?**

> 它们解决的是我们规模下不存在的计算问题,而引入的是真实成本:重依赖、过滤短板(FAISS 系元数据过滤很脏)、以及评测复现的外部变量。我们的金标评测要求 must_stale 每次提交可复现,检索层确定性越高越好。

**Q:这套东西在简历上怎么一句话说?**

> 「面向主张复验的确定性检索层:SQLite 元数据过滤 + 可插拔多 stage 打分管线,按语料规模分级启用词法/向量路,召回升级由评测熔断条件触发而非预设。」
