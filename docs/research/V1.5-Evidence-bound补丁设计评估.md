## 1. 问题 + 前置约束

对客尖刀与论文主投（idea #2）要求：改稿必须引用已入库 T1、人确认后才落地、立刻再验、证据可导出。V1 已有「需补丁」展示与 `patch_events` 起记，但**没有**改主张正文的 attested 闭环；HumanLatch 仍只有 `discard`/`renew`。

| 前置 | 来源 | 锁死作用 |
|------|------|----------|
| V1.5 In/Out/Exit 骨架；不定 mid 生死；不得替代 I1 | roadmap | Exit=闭环 demo+导出，非 n≥30 |
| 包结论三值；底部主张态不改名 | ADR-0027 | 补丁改的是主张正文，不是第四套 disposition |
| C vs T 不进发前 UX；patch_events JSONL 已起 | ADR-0027 | 产品路径恒 T；C 仅脚本 |
| HumanLatch 动词不因 I1 三分法扩枚举 | ADR-0028 | 补丁 API 宜独立，勿塞第三 latch 动词凑语义 |
| 垂直=顾问报告；样例包 `v1-mck-soai` | ADR-0027 | Exit 脚本复用 mck-* |
| 禁「首次带证据改稿」；少用 proof-carrying | roadmap / contribution-boundary | 对外 attested / evidence-bound |
| Anthropic：demo≠统计；预锁 Exit；随机系统不单次判生死 | 纪律清单 | Exit 不硬要「可发」 |

验收层：**冒烟·对客 demo**（非 C vs T 统计结论）。

## 4. 拍板 + 子决策

1. **补丁** = 整条 `statement` 替换 + 必填 `t1_ids` ⊆ 本 Run 已入库 T1；fail-closed。  
2. **API** = `propose_patch` / `confirm_patch`（Verify+）；**不扩** HumanLatch；confirm 后单条再验 → 重算 disposition；`arm=T`。  
3. **UX** = 复验单/Run 详情增量；资格 = 未 discard 的 `unknown`|`stale`。  
4. **草案** = 会话/Run 暂存；未 confirm 不改正文、不写正式 `patch_events`。  
5. **账本** = 增 `before_text`/`after_text`；保留 `patch_span`（可自动默认）；`minutes` 确认时手填。  
6. **导出** = JSON + 短 Markdown。  
7. **薄对话** = 本期 Out；roadmap In 改为表单闭环。  
8. **Exit** = `docs/evidence/v15/ACCEPTANCE.md`；脚本 discard mck-1&4 → patch mck-3 → …；硬条不含「可发」。  
9. **#8 / n≥30** = 不挡本期；论文蓄数并行。  
10. **ADR-0029** + 本评估 + CONTEXT 词条。

## 6. 面试讲法

**Q: 你们的对客尖刀和 Claim OS / PCC 有何不同？**  
A: 我们卖的是发前 **evidence-bound / attested patch**：改稿必须引用 ⊆ 已入库 T1，人确认才落地，立刻再验，证据可导出。不装形式化 proof-carrying，不吹首次发明；组合协议见贡献边界。

**Q: 为什么补丁不做成 HumanLatch 第三个按钮？**  
A: 作废/续命是红黄灯收口闩；带证改稿是 Verify+ 另一条缝。混进 renew 或第三动词，面试讲不清，也容易和 I1「不扩生产枚举」纪律打架。

**Q: Exit 为什么不要求改完就「可发」？**  
A: 冒烟层硬条锁确定性（硬闸、确认、再验触发、导出）。包结论升「可发」依赖 Gate/模型，单次跑判生死不合格；升可发是加分演示，不是 Exit 唯一判据。

**Q: 薄对话呢？路线图不是写了吗？**  
A: grilling 后改表单 Exit；薄对话本期 Out、评估留位。避免半截聊天框冒充已交付，也避免对话改正式裁决。

**Q: 论文 C vs T 怎么做？**  
A: 产品路径恒 T；C 只脚本写同一 `patch_events`。n≥30 不挡产品 Exit；冲 Findings 另蓄数。单次 demo 不报显著。
